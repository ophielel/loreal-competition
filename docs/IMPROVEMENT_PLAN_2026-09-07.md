## 1. 结论与投入方向

项目已经具备完整竞赛原型的基础：三栏客服工作台、官方数据导入、历史回放、规则与 Qwen 融合、证据定位、人工确认任务、PPT、视频和源码包都已存在。继续投入最有价值的方向是：**把现有“能展示分析结果”的原型，完善为能够减少重复询问、提出有依据的下一步行动、追踪风险处理结果，并能量化证明这些价值的客服辅助工具。**

建议保持现有 Python、原生前端、SQLite 架构，将开发资源集中在五件事上：

1. 修复已经复现的判断与证据问题，统一代码和提交材料版本。
2. 将原始主诉、当前诉求、情绪与风险分开建模，改善多轮判断。
3. 深化聊天、订单、工单的关联，让“已知什么、还缺什么、下一步做什么”直接可用。
4. 建立独立评估与小规模客服任务实验，为比赛展示提供效果证据。
5. 将演示与材料围绕三个完整服务案例重新组织，展示在线模型的实际贡献。

不建议近期重写前端框架、拆微服务、建立复杂多 Agent 协作、全面微调模型或接入真实退款系统。这些工作对当前比赛表现的收益较不确定，而且会挤占上述关键任务。

## 4. 主要发现与优先级

本计划的 P0 表示下一次正式演示或打包前优先处理，P1 表示提升作品竞争力的核心建设，P2 表示前置工作通过后再投入。

### P0-A 风险规则不能区分实际发生、否定和假设

位置：[engine.py](D:/oly1/src/engine.py:20)、[model.py](D:/oly1/src/model.py:84)。

本次直接调用当前规则函数复现：

| 输入 | 当前输出 | 应改进的判断 |
|---|---|---|
| 我没有过敏，只是想问这款面霜的成分 | 不良反应、高关注 | 否定已发生不适，主要是产品咨询 |
| 这款精华会不会引起过敏？ | 不良反应、高关注 | 假设性产品问题，不应写成已经使用不适 |
| 之前一直没有投诉，这次想查一下物流 | 物流服务，但高关注投诉风险 | 识别否定范围，避免无依据投诉预警 |
| 用了以后脸上像针扎一样，眼皮也鼓起来了 | 待确认、普通、无风险 | 作为使用后不适线索优先人工核实，不能因为未命中关键词而忽略 |

健康门控目前会保留规则产生的高关注结果；因此规则误报即使遇到模型正确判断，也可能继续触发专员分流。应保留对明确不适的保护，同时让规则输出包含“实际发生／否定／假设／既往／待核实”及证据，避免让所有含风险词的句子直接进入同一门控。

### P0-B 风险触发和证据提取使用了不同条件

位置：[engine.py](D:/oly1/src/engine.py:103)。

“脸上起了好多小疹子”能命中 `起.*疹` 正则，却不命中提取证据使用的关键词列表，因此出现高关注提示、`evidence_ids=[]`。

在官方数据的全部回放时点中，还发现 9 个“情绪有升级迹象”提示没有证据，涉及 S00074、S00097、S00226。S00226 是从“开发票，谢谢”进入提供抬头和税号，规则把“缓和 0 → 平稳 1”视为情绪升级；这既暴露证据缺失，也暴露趋势定义不合理。

建议由同一个匹配结果同时生成风险和引用。情绪升级需依据连续催促、明确负向表达或冲突加剧等事件，不能仅比较首尾两个任意编码。没有可用证据时应撤销该结论或明确标记待核实。

### P0-C 结构校验不等于回复可信

位置：[model.py](D:/oly1/src/model.py:37)、[model.py](D:/oly1/src/model.py:68)。

当前验证字符串、长度、枚举和可见 ID，但没有逐条验证回复中的业务事实。离线构造一条带合法引用的模型结果，回复为“已为您完成退款，明天一定到账。”，在订单服务一致判断路径中可以通过 `validate()` 并被 `merge_hybrid()` 保留。

这是校验器边界的合成反例，**不表示真实在线模型已经输出过该承诺**。应增加事实与行动校验：无执行回执不能说已执行，无政策或工单依据不能保证具体到账时间，客服历史承诺也不能自动转成系统的新承诺。失败时保留安全的核实建议，并显示拦截原因。

### P1-B 模型输出未覆盖完整的业务判断维度

目前模型返回单一主意图和单一情绪；没有独立结构化风险数组。模型只有在主意图为“不良反应”时才额外提升健康关注，无法完整表达“当前退货诉求，同时有健康不适、重复催促与待完成工单”。模型可以更新情绪文字，但趋势仍来自规则，优先级也没有统一根据模型情绪重新计算。

建议保留“原始主诉”用于官方标签口径，新增“当前诉求、风险事件、当前处理阶段”。每一项带当前可见证据，所有最终优先级与操作建议由同一决策层计算。

### P1-C 多源数据已经关联，但业务融合还偏浅

位置：[model.py](D:/oly1/src/model.py:112)、[app.js](D:/oly1/web/app.js:72)。

订单模型上下文目前主要是商品、金额、状态，工单主要是类型、状态与时间；具体问题、关联对象和已采取措施没有充分进入推断。大部分价值停留在数据展示。存在任意工单就提醒避免重复创建，也没有区分同一业务事项、开放或完成工单。

建议以当前会话为范围创建“服务事项卡”：用户已提供的信息、对应订单与工单、客服说法、已核实事实、缺失字段、仍未解决的问题、下一步可做动作。先完成一个会话内的事项整合，再考虑跨会话关联。数据不支持可靠客户身份时，不能靠昵称强行合并。

尤其需要补上“避免重复提问”的实际机制：如果订单号、诉求或相关说明已在可见消息中提供，建议里不应再次索要；如果缺少关键字段，只问下一步真正需要的一项。

### P1-D 跟进任务尚未形成风险处理闭环

位置：[store.py](D:/oly1/src/store.py:13)。

当前只有标题、备注、会话、回放点、创建时间，以及“待处理／已完成”。缺少风险类型、责任人、截止时间、处理经过、关闭原因和结果证据；去重键为会话＋回放点＋标题，换一个回放点或标题就可能重复创建同一事项。

建议新增简单风险队列，围绕业务事项去重，采用“待确认→处理中→待回访→已关闭”，允许误报关闭与重新打开。必须用实际结果说明关闭，不把点击完成等同于已退款、已解决或客户满意。

### P2-A 成本设计已经存在，优化收益需要实测

本次从保存的在线响应记录计算，首条消息场景延迟中位数约 4.99 秒、P95 约 6.84 秒；完整会话中位数约 5.36 秒、P95 约 7.42 秒。这里采用排序后 `floor(0.95×(n−1))` 对应值，是历史调用记录耗时，不是今天重测的浏览器端到端延迟。

当前所有场景点击后都走同一调用方式，完整快照缓存难以复用每个新消息时点；缓存锁也没有合并尚在执行中的相同请求。前端 `modelBusy` 为全局状态，一个会话等待期间会阻止其他会话调用。后端返回了仲裁来源和模型延迟，界面未充分展示。

先记录冷启动／缓存命中／超时与回退延迟，再实验选择性调用和请求合并。不能用只有规则函数的亚毫秒耗时代表完整 Agent 性能，也不能只报告 token 节省而省略质量退化。

## 5. 推荐的目标流程

```text
新消息或回放时点
  → 可见数据与身份边界检查
  → 会话内服务事项整合
  → 原始主诉 + 当前诉求 + 风险事件识别
  → 已审核知识与现有工单检索
  → 生成摘要、待核实信息和下一步建议
  → 逐项证据校验 + 承诺及执行状态检查
  → 客服编辑与确认
  → 本地跟进任务、处理日志和回访结果
```

实施原则：

- 先做一个完整案例贯通各步骤，再扩展到三个案例。
- 模型负责语义理解与候选建议；证据时点、权限、执行回执和任务状态由确定逻辑约束。
- 将风险“识别是否存在”和风险“处理是否结束”分开，后续一句谢谢不直接清除风险，也不意味着永远不能关闭风险。
- 历史回放、归档分析和补充模拟事件分别标注。所有新知识、图片和事件都能说明来源。
- 数据规模较小时优先结构化查询和轻量文本检索，只有检索评估发现明显收益才引入向量数据库。

**T02 统一风险与证据生成｜0.5—1 天｜依赖：无**

## 7. 验收指标与实验纪律

下面是建议的开发验收目标，不是已经达到的效果，也不是官方规定的分数线。完成试标后可基于样本难度调整一次并冻结，不能看到留出结果后再改门槛。

| 维度 | 建议验收条件 | 报告要求 |
|---|---|---|
| 证据完整性 | 官方所有回放时点的确定性风险均有可见依据；固定测试中未来证据泄漏为 0 | 引用存在性与语义支持分别统计 |
| 回复可靠性 | 冻结阻断集中无依据执行／赔付／到账承诺漏放为 0 | 有限测试通过不等于生产风险为 0；同时报告误拦截 |
| 主意图 | 独立集 Macro-F1 不低于冻结规则基线；报告各类变化 | 区分原始主诉、当前诉求与信息不足时点，报告样本数 |
| 风险识别 | 探索目标：重点风险召回 ≥95%，否定和假设负例正确率 ≥90% | 在有足够正负样本和人工金标后计算，给出区间或逐项计数 |
| 证据语义 | 探索目标：人工审核的关键事实支持率 ≥95% | 审核单位为事实断言，不能用合法 ID 数代替 |
| 业务流程 | 已知字段不重复询问；高风险事项可追踪到处理记录 | 在固定任务集报告重复提问和遗漏次数 |
| 成本性能 | 同条件下调用或 tokens 至少降低约 20%，关键质量不退步 | 首先作为实验假设；必须计入重试、回退、缓存与请求失败 |
| 客服使用价值 | 在准确性不下降前提下，探索定位耗时下降约 20% | 报告中位数、个体差异、样本规模；未达目标照实呈现 |
| 提交可复现 | 空目录解压启动、测试与文档链接检查全部通过 | 附源码、数据与评估版本，不只检查 ZIP 能解压 |

风险、情绪、证据质量和共情表达建议由两人独立审核并仲裁。共情评分可分为是否准确理解当前处境、是否避免重复索取信息、是否给出具体下一步、是否使用不合适的模板措辞；不以“回复越长越共情”作为标准。

留出数据只用于冻结候选的最终评估。需要比较多种架构、提示词或模型时，先在开发数据上完成选择。因已经阅读现有官方错误样本，不能再宣称这些样本对开发者不可见。

## 8. 参赛展示建议

将展示主线固定为三个案例，每个案例呈现输入、证据、建议、人工动作和结果：

1. **多次催退款**：从当前主诉识别已提供订单信息，区分普通退款进度与独立打款；查已有处理记录，只追问缺失项，创建具体跟进。
2. **退货伴随使用不适**：保留退货主诉并独立提示不适风险；显示正确原文；拦截未经核实的承诺；由人工确认下一步。
3. **物流异常后的补发**：原始问题仍是物流异常，当前处理阶段为补发或待跟进；正确关联工单，避免重复建任务，说明结果来源。

官方工单在历史聊天结束后才创建，因此实时部分展示“当时可见信息下如何辅助”，归档部分展示“事后如何核对已处理状态”。如果需要展示后续回访事件，使用单独标注的补充模拟数据。

建议录制 2—3 分钟精简版本，时长最终服从提交页要求。展示一次真实模型成功路径、一次模型与规则分歧处理、一次失败后继续工作的路径。主画面优先呈现消费者问题和客服操作，模型参数与技术架构放到对应说明页。

PPT 可控制在约 10—12 页：问题与用户、工作台约束、核心案例、三源融合、风险与证据、Agent 流程、独立评估、使用价值、性能成本、落地及交付。现有重复封面和泛化口号页可压缩，给实测案例与结果留出空间。
